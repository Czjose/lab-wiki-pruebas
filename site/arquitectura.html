Cómo está montado

Arquitectura del sitio

Esta wiki son archivos HTML, CSS y JavaScript comunes. Lo interesante es cómo llegan a tu navegador: un servidor Nginx que corre dentro de un contenedor Docker y lee los archivos directamente de la carpeta del proyecto.

Las piezas, una por una

Imagen
El molde. Es un paquete de solo lectura con todo lo necesario para ejecutar algo; aquí, nginx:alpine. Se parece a una ISO: por sí sola no hace nada.
Contenedor
El molde funcionando. Es un proceso aislado creado a partir de la imagen, como una máquina virtual encendida, pero mucho más liviano. El nuestro se llama wiki-pruebas.
Nginx
El servidor web. Recibe las peticiones del navegador ("dame index.html") y devuelve el archivo correspondiente, o la página 404 si no existe.
Puerto publicado 8080:80
Una puerta que conecta dos mundos: la puerta 8080 de tu PC queda enlazada con la puerta 80 del contenedor. Por eso entras por http://localhost:8080 aunque Nginx escuche en el 80.
Bind mount ./site → /usr/share/nginx/html
El contenedor "ve" tu carpeta del proyecto como si fuera suya. Editas un archivo en VS Code, refrescas el navegador y el cambio ya está. Se monta en solo lectura (:ro) para que Nginx no pueda modificarla.
Persistencia
El contenido vive en tu carpeta, no dentro del contenedor. Si borras el contenedor con docker compose down, no se pierde nada: al levantarlo otra vez vuelve a leer los mismos archivos.
Healthcheck
Una revisión automática: cada 30 segundos Docker ejecuta wget dentro del contenedor contra la portada. Si responde, el estado es healthy; si falla tres veces seguidas, pasa a unhealthy.
Dockerfile (imagen propia)
La alternativa al bind mount: copia el sitio dentro de una imagen nueva. Es ideal para entregar o desplegar, pero cada cambio exige volver a construir la imagen.

Levantarlo y detenerlo

Desde la carpeta del proyecto, en PowerShell:

docker compose up -d      # crea y arranca el contenedor en segundo plano
docker compose ps         # muestra el estado; tras ~30 s debe decir "healthy"
docker compose down       # detiene y borra el contenedor (tus archivos siguen intactos)

Y con la imagen propia, construida a partir del Dockerfile:

docker build -t wiki-pruebas:1.0 .
docker run -d --name wiki-img -p 8081:80 wiki-pruebas:1.0

Pruebas al contenedor

Revisar que el sitio funciona también es probar software, y cada comprobación encaja con un término del glosario:

PruebaCómo se haceEnfoque del glosario
Abrir la página y verificar que responde curl -I http://localhost:8080 debe devolver 200 OK; una ruta inexistente, 404. Caja negra / prueba de humo: solo miramos la respuesta.
Revisar el interior del contenedor docker logs wiki-pruebas y docker inspect wiki-pruebas muestran las peticiones, la configuración y el estado del healthcheck. Más cercano a caja blanca: miramos cómo funciona por dentro.
Comprobar que Nginx entrega los archivos del volumen Editar un archivo de site/, refrescar y ver el cambio; verificar que CSS y JS llegan con 200. Integración: Nginx, el bind mount y el navegador trabajando juntos.

En la práctica

El indicador del pie de página dice "Servido con Nginx en Docker" cuando la página llega por http://. Si abres index.html con doble clic, dirá que está abierta como archivo local: el contenido es el mismo, pero sin servidor de por medio.
